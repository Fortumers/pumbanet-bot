# Хранилище платежей и transactional outbox

Это дополнительный слой проекта, не готовый бот.
Старый README описывает первый модуль; актуальное дополнение находится здесь.

## Реализовано в коде

SQLAlchemy-модели клиентов, заказов, платежей и задач; начальная миграция
Alembic; атомарная запись платежа, статуса paid и задачи; блокировка заказа;
глобальная уникальность идентификатора платежа; повторная доставка задачи
после истечения аренды; fencing token для подтверждения задачи; backoff;
ограничение числа попыток; интеграционные тесты и PostgreSQL в CI.

accept_payment не проверяет подлинность платежа. Вызывать его можно только
из доверенного платёжного адаптера после проверки серверного события.
False означает уже записанный платёж, а не ошибку или новую выдачу.
IntegrityError при конфликте charge_id откатывает всю транзакцию; адаптер
должен отдельно расследовать конфликт, не объявлять его успешной оплатой.

## Проверка в отдельной тестовой базе

Требуется Python 3.11+ и PostgreSQL. Не используйте базу клиентов для тестов!
Пароль в URL должен быть URL-encoded. Секреты храните вне GitHub.

```sh
python -m venv .venv
. .venv/bin/activate
pip install -r requirements-storage.txt
export DATABASE_URL='postgresql+asyncpg://USER:PASSWORD@HOST:5432/TEST_DB'
export TEST_DATABASE_URL="$DATABASE_URL"
alembic upgrade head
alembic check
python -m unittest discover -s tests -v
python -m unittest discover -s integration_tests -v
```

В тестовой базе не должно быть других ожидающих задач: тесты claim_job
проверяют глобальную очередь. CI поднимает отдельную пустую базу.
Миграции применяются отдельно, приложения не используют create_all.

## Ограничения

Зависимости SQLAlchemy/Alembic/asyncpg отсутствовали в среде разработки
этого пакета. Локально проверен синтаксис, НЕ запуск PostgreSQL-тестов.
Результат интеграционных тестов должен быть проверен после коммита в CI.
SQLite пока не поддерживается этим адаптером; доменные правила не зависят от БД.

Нет Telegram-интерфейса, payment adapter, воркера Remnawave или реальной выдачи.
Нельзя трактовать Job.done как Order.fulfilled. finish_job подтверждает только
обработку задачи; завершение заказа должен делать будущий provisioning service
после проверки аккаунта, сроков, групп, лимитов и настоящей subscription URL.

Очередь обеспечивает at-least-once. Fencing защищает изменения в БД, но не
внешние действия Remnawave. До подключения панели необходимы сериализация
выдачи на пользователя, устойчивый план операции, проверка результата после
таймаута и безопасное продление аренды. Пока API-вызовов и воркера нет.

Создание заказов пока доступно только через модель; тарифная админка и
снимок условий из каталога ещё не подключены. Возвраты и сроки оплаты
не реализованы. Задачи со статусом failed требуют будущего операторского
интерфейса повторного запуска и уведомления администратора.

Не храните токены, ссылки подписок и тексты исключений в outbox.
error_code допускает только короткий ASCII-код, например panel_unavailable.
